# 对话分工与标准文档

版本：v1.3。制定及修订日期：2026-10-18（北京时间）。00项目总指挥维护全局规则与状态；主控、视觉、硬件维护各自模块证据。03在G-01中补充版本交接记录入口。

本文件规定后续工作的对话归属、文档依据和交接方式。当前对话承担00项目总指挥；其它执行对话由主控初始化或复用，本文件不代表已完成其创建、改名或归档。

### 归属判断

1. 三方任务、时间、范围、接口变化及交付阻塞统一进入00。
2. 主控代码、开发工具及独立模块验证进入01。
3. 整车装配、跨板连接与实际车辆表现进入02。
4. 02定位到主控缺陷后转01修复；视觉或硬件缺陷记录为对应角色的交付问题，明确证据与复测条件，不默认由主控接管其实现。
5. “主控采购的物品如何接入整车”进入02；“如何编程使用”进入01；“交付依赖和时间影响”汇总到00。
6. GitHub上传、分支、PR、合并及台式机/笔记本版本交接进入03；交付范围由00梳理，远端操作仍以主控明确授权为准。

例如视觉缺扬声器：00记录交付依赖，由硬件提供物品、视觉验证播放；02在最终拼组时检查音频功能与车辆动作是否衔接。主控无需负责音频驱动或识别算法。

### 尚缺的两类正式硬件记录

以下资料由硬件提供或共同实物核对，02接收并记录最终拼组使用的版本。当前尚未创建，属于外部交付及联调记录项：

- `hardware_preparation/hardware_inventory.md`：实际器件型号与版本、数量、采购角色、当前保管角色、到货/验收状态、订单或照片、缺项。采购角色与使用/保管角色分开记录。
- `hardware_preparation/wiring.md`：板卡版本、MCU端口与物理针脚、对端接口、电平、供电与共地、电机方向、编码器极性、照片、核对角色、接线版本。未核对项写“待核对”。

这两份记录建立后分别作为实物清点和装配接线的主要依据；`pin_plan.md`继续负责软件资源分配，引用同一接线版本。

### 草案冻结

协议共同确认后，优先在原文件标明版本、确认日期、角色和验证范围；保留现有路径，减少断链。冻结表示接口已达成约定，实物通过情况仍需测试记录。格式或单位发生不兼容变化时，记录新版本、影响端及同步修改的代码。

语音动作反馈目前尚未实现；增加反馈时扩展同一协议入口，避免主控、视觉各保留不同版本的“最终协议”。

## 3. 冲突怎样处理

依据按问题类型判断：赛事要求查官方资料，实际行为查相应版本的代码和测试，工作安排查已确认的计划与决定。文件日期较新本身不足以证明内容正确。

1. 主控明确的新决定记下原话含义、日期、影响范围和来源；未回答的提议保持“待确认”。
2. 文档与代码冲突时，分别记录“约定行为”和“当前实现”，建立修复项；代码的现状不自动改写双方约定。
3. 状态更新必须链接证据。只有代码或电脑测试，标明实现/电脑验证范围；只有聊天口头汇报，标明“口头确认、待归档”。
4. “未找到证据”写为“待核实/未归档”；只有从源码确证缺失时，才写“未实现”。
5. 冲突登记在 `project_status.md`，写明处理角色、具体源文件和下一步；在解决前告知受影响的模块对话。

当前已发现的冲突和缺项已录入状态表；它们是后续工作入口，不能直接当成已修订的PDF内容。

## 5. 开工、收工与交接

各对话的可复制初始化文本见 [对话初始化Prompt](agent_initialization_prompts.md)。初始化先读取文件并回报职责、事实与下一步；实际开发、测试按随后明确的任务推进。

### 主控汇报与00分配

主控可直接用自然语言说明新需求、完成事项、遇到的问题或现场变化。00先核对仓库和已有证据，区分口头汇报、已实现、已验证及待验收，再更新关联记录。对无法从现有资料取得、且影响执行的必要信息集中询问；其余独立工作继续推进。

00每次返回当前判断、执行顺序和可直接复制的任务Prompt；没有后续任务时明确说明无需分配。Prompt包含：任务ID、目标agent/责任角色、背景与依据、任务目标、读入文档与代码版本、可改范围、步骤、前置依赖、验收标准、本次授权和结果回报格式。多项任务按依赖顺序给出；同一目录的写入、分支切换与板卡操作顺序执行。主控将Prompt转交目标对话，再把结果带回00验收与安排下一步。

生成Prompt不等于已发送、已开工或已有远端授权。00不自动给其它聊天发消息。对于视觉、硬件事项，Prompt面向对应角色交付，不要求主控完成其具体实现。

### 开工

读取 `AGENTS.md`、本文件、`project_status.md`，再读取任务相关的模块文档。确认任务ID、目标和本次工作目录、分支及未提交改动。主控已授权的清晰任务直接执行；排期、接口等重大未决决定按项目默认技能处理。

多个对话使用 `D:\Projects\yeye` 时会共享工作文件和当前Git分支。同一文件同时只由一个对话写入；切换分支前先确认其它工作已保存且没有并行写入。聊天按主题分开，不会自动产生独立工程副本。

### 收工

1. 保存实际成果与对应验证，更新模块文档。
2. 更新状态表中的关联任务、证据和下一步。通常只需更新一行，避免每次重写整体规划。
3. 使用下列短交接格式，明确测试范围与本地保存情况。

```text
任务ID：例如 C-01（示例）
负责角色／所属对话：主控／01
完成：具体变化及文件位置
验证：日期、方法、结果、版本；哪些项目仍待实测
阻塞／待确认：具体问题及依赖角色
下一步：一个可执行动作
版本位置：工作目录、分支、提交号或“有未提交修改”
同步情况：仅本地／本次获授权后已上传；远端分支与提交
```

主控只需在目标对话提供任务ID和文档路径，即可续接工作。若需要另一个对话处理问题，先保存上述交接；向其它对话发消息仍需主控明确授权。

### 上传与跨电脑

所有对话默认保存、验证本地成果。主控明确要求上传当前改动后再推送或更新远端PR；历史上传请求不延续到新任务。教程的收工Push步骤是人工协作示例，不构成Codex自动上传授权。

依靠Git传递已提交并上传的项目文件，交接时核对分支和提交号。尚未上传的本地修改、IDE配置和被忽略的原始证据须另行说明。新电脑先读取同一套标准文档，再核对实际工具与板卡连接。
