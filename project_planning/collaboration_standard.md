## 闭环与写入顺序

1. 总管定义一个成果任务，写目标、依赖、允许范围、评分关联、交付物、结束条件和适用检查。重大未决设计按项目技能询问；已确认事项直接执行。
2. 主控转交任务路径及当前授权；执行对话核对目录、HEAD、已有修改和当前设备占用。收到Prompt不等于已开工。
3. 执行对话实现并保存必要证据，实质进展、阻塞或收工时更新同一任务；可交付改动及适用检查完成后按下述Git规则做本地提交，软件交付进入“待主控验收”。
4. 主控明确通过／退回及范围；执行对话或总管如实记录原话、日期与证据，不代作决定。主控退回则继续原任务。
5. 主控将任务路径和新反馈交给总管。总管读取摘要与必要原证据、记录人工结论，再顺序更新全局状态并分配下一项；不要求重跑检查代替阅读证据。

状态：待核实／未开始／进行中／待主控验收／已验收／已关闭。阻塞独立记录；关闭须写终止或替代原因。中断不是关闭；换聊保持任务ID。软件、板级、整车分层验收，部分通过不扩大范围。

同一checkout默认一个执行写入者，Keil保存／构建／分支／下载／设备连接串行。并行实现须先明确独立worktree、来源提交、未提交及忽略文件的处理、合回负责人和检查。总管与执行对话不得同时修改同一任务文件。

## Git 本地提交与版本交接

本规则自2026-11-19主控确认后适用于后续执行交付。本地提交用于把代码、适用证据与任务状态对应起来，降低错版、丢失修复和重复调试造成的完赛风险，支撑比赛表1基本功能60分及报告20分；提交号和Git检查本身不证明比赛得分或车辆通过。

- **默认本地提交。** 执行对话完成一个可交付改动及适用检查后，应在交付前做本地`git commit`，无须为已授权任务的每次本地提交再次询问。主控明确要求暂不提交时按该要求执行并记录。提交粒度以可说明、可追溯的成果为准；同一任务可包含多个必要提交，不要求每轮对话提交一次，也不强制每任务新建分支。中断时可保存明确标为接续／失败的检查点，不把它写成验证通过。
- **只提交明确范围。** 开始时核对分支、完整HEAD、工作区及暂存区；提交前检查实际差异，使用明确路径或改动块暂存，并审阅暂存差异。不得使用`git add .`或`git add -A`批量夹带无关改动。文件同时包含本任务和已有共享修改时按改动块选择；无法安全分离时保留现场，报告未提交范围与原因，由总管界定版本整理任务，不清空或覆盖现场。已有暂存内容也不能擅自取消或一并提交。
- **标识与交付。** 提交信息采用`<完整任务ID>: <改动说明>`，例如`I-04-RIGHT-ANGLE: 修复日志保存与发送间隔`；说明必须符合实际改动。先更新同一任务的改动、检查、待验与限制，再提交。最终回报给主控分支、完整提交号、提交范围，以及剩余未提交／未上传项；换聊以该提交及剩余工作区差异接续。不要为把本次提交号写入其自身文件而循环提交。
- **检查与人工验收分开。** 检查只按改动影响选择，相同适用证据可复用；不能为提交追加无依据测试。提交时资料／软件／板级／整车状态分别如实记录，软件提交可以处于待主控验收。主控验收或退回后在原任务记录反馈，相关后续修改正常追加提交；不以本地提交、上传或标签代替验收，不擅自amend、reset、强推或改写已有历史。
- **权限与职责。** 本地提交不包含上传、更新远端PR、合并、发布或设备操作授权；这些仍按主控本次明确范围执行。已允许运行某类Git命令不等于获准扩展任务。总管维持管理职责，不代替执行对话整理、提交实现代码。历史积压和其它任务成果不能因本规则生效自动并入当前提交。

## 上下文与检查边界

新对话读取规则、短状态及指定任务当前区；只按需要读取模块规格、源码与证据。历史区旧Prompt和“下一步”不作为当前指令。总管完整启动与执行模板见[初始化提示词](agent_initialization_prompts.md)。

按改动选择检查；相同适用版本／配置／输入／环境复用证据。文档改动只检查链接、路径与一致性，不自动跑固件回归。测试通过或预定验收满足后结束，不自增测试矩阵。人工试跑沿用一次双轮悬空、随后一次上道；保护不删，接线确变时具体说明核实项。

默认本地保存，执行交付按上述规则做本地提交。上传、远端合并、发布、跨聊天发送及设备动作按主控本次授权；旧上传和旧板卡授权不延续。历史日期、失败和证据保持，缺证标待核实，不以日期新旧代替事实判断。
